Chapter 1 · Fundamentals & How LLMs Work

1.1 What is a Large Language Model (LLM)?

A Large Language Model (LLM) is a deep neural network trained on massive text corpora, whose core task is to predict the next token. It doesn't truly "understand" the world — it learns an extremely powerful text probability distribution: given the preceding text, predict the most likely next word/subword.

Because training data covers nearly the entirety of human-written knowledge, the model learns patterns of grammar, logic, common sense, code, and even reasoning. When you type a prompt, it generates a reasonable response token by token, based on contextual probabilities.

1.2 Key Terminology

TermMeaning
TokenThe smallest text unit the model processes — can be a word, subword, or character. In Chinese, ~1 token per character; in English, ~1.3 tokens per word.
Context WindowThe total token limit (input + output) the model can "see" at once, e.g. 8K / 128K / 1M.
ParametersThe number of internal weights, e.g. 7B = 7 billion, 70B = 70 billion. More parameters generally mean stronger capability.
PretrainingThe phase of learning language patterns from massive unlabeled text, producing a "base model."
AlignmentThe training phase that makes the model follow instructions, conform to human preferences, and meet safety requirements.
InferenceThe process of using a trained model to make predictions on new input (i.e., "generating responses").
Generative vs. DiscriminativeLLMs are generative models — they "create" new content, not just classify.
TemperatureControls output randomness. Low temperature = more deterministic; high temperature = more diverse.
Top-p / Top-kSampling strategies that restrict selection to the top-k highest-probability tokens or those with cumulative probability ≤ p.
✅ Minimal understanding: An LLM = "a giant probability machine that has read nearly all text, writing the most reasonable answer one word at a time." Grasp this, and everything else connects.

1.3 Why Does "Predicting the Next Word" Produce Intelligence?

This is the most counterintuitive yet crucial point: how can a model that merely "predicts the next word" write code, reason, and translate? The answer: to predict the next word accurately, the model must internally learn grammar, logic, common sense, knowledge associations, and even some degree of reasoning — just as a person needs to truly understand a sentence to continue it naturally.

When training data reaches massive scale and parameters exceed tens of billions, Emergent Abilities appear — capabilities that "suddenly" emerge at a threshold rather than improving smoothly, such as few-shot learning, code generation, and multi-step reasoning.

1.4 Autoregressive Generation: How "Word-by-Word Output" Works

LLM text generation is an autoregressive process:

  1. Input the user prompt; the model predicts a probability distribution for the first token;
  2. A token is selected via sampling strategy (temperature / top-p);
  3. The new token is appended to the context, and the next token is predicted;
  4. Repeat until an end-of-sequence token or maximum length is reached.
Input:  "The capital of China is"
Step1:  P(Beijing)=0.82  P(Shanghai)=0.10  P(Nanjing)=0.05 ...
Pick token → "Beijing"
Input:  "The capital of China is Beijing"
Step2:  P(.)=0.95  P(!)=... → Pick "."
...
Final:  "The capital of China is Beijing."

1.5 Generation Modes: One-Shot vs. Streaming

In practice, the model can output a complete response at once, or return tokens streaming (typewriter effect). Streaming has lower first-token latency and better UX, making it the standard for chat products.

1.7 Chinese Models & Tokenizer

Chinese tokenization differs from English. A good tokenizer merges common characters/words into single tokens to reduce sequence length and improve efficiency. This is why different models consume different token counts for the same Chinese text.

One Chinese sentence (~20 chars)~10–18 tokens
One page of Chinese (~500 chars)~300–450 tokens
💡 Remember: you're talking to a giant probability machine, not a conscious entity. Understanding this helps you design prompts and evaluate outputs more rationally.

Chapter 2 · Model Architecture: Transformer & Attention

🎬 Intuition first: Don't rush to memorize formulas — grasp the development storyline first:
① Everything can be viewed as a function (early "symbolism" tried to write exact functions, but humans can't write "recognize a cat") → Shift to connectionism: accept approximations;
② Use a line (y = wx+b) to approximate, adjusting w and b iteratively → Lines are too rigid, add activation functions to bend them, enabling infinite nesting;
③ Draw this "linear transform + activation" nesting as a graph — each node is a neuron, layers connected = neural network; computing left to right = forward propagation;
④ Everything else (backprop, gradients, Transformer…) is essentially solving for those w, b (weight matrices).
With the mindset that "all models are just guessing a set of function parameters," attention, multi-head, and MoE are just branches on this tree.

2.1 From RNN to Transformer: Why Attention?

First, turn text into numbers: Computers only process numbers, so each word must be encoded into a vector. Simple numbering (one number per word) is too low-dimensional; One-hot encoding is too sparse and high-dimensional, with all words orthogonal. Enter Embedding — mapping each word to a moderate-dimensional vector where dot product / cosine similarity captures semantic closeness (even "king - man + woman ≈ queen"). These word vectors are the input to the neural network.

The original sequence model, RNN, uses a hidden state to pass information across tokens. But it has two fatal flaws: information degrades over long sequences (long-term dependency problem), and it must process tokens sequentially (no parallelism). GRU/LSTM only mitigate, not solve these.

In 2017, Google proposed the Transformer (paper: Attention Is All You Need), using self-attention to solve both: every token can "directly see" all other tokens, and computation is parallelizable. Attention replaced recurrence as the mainstream.

2.2 Self-Attention Core Idea

For each token, the model generates three vectors: Q (Query), K (Key), V (Value). The core logic is "who I should attend to, I take information from":

  1. Each token's Q is dotted with all tokens' K to get attention scores;
  2. Scores are softmax-normalized into weights;
  3. Weights are used to compute a weighted sum of all Vs, producing the token's new representation.
Attention(Q,K,V) = softmax( Q·Kᵀ / √d_k ) · V

Q·Kᵀ  →  compute "who relates to whom" scores
/√d_k  →  scale to prevent large values, gradient vanishing
softmax → normalize into probability weights (sum to 1)
·V     →  fuse "value" info by weights

2.3 Multi-Head Attention

Instead of one set of Q/K/V, split into multiple "heads," each learning different relationships in different subspaces (some capture syntax, some coreference, some semantics), then concatenate. This lets the model simultaneously capture multiple aspects of information.

2.4 Positional Encoding

Attention itself doesn't distinguish order ("A sees B" and "B sees A" have equal weights). To inform the model of word order, positional information must be injected. Common approaches:

  • Sinusoidal positional encoding (original Transformer);
  • RoPE (Rotary Position Embedding): encodes position into Q/K via rotation matrices, widely adopted by open-source models, friendly to long contexts;
  • ALiBi: adds distance-based bias to attention scores, strong extrapolation.

2.5 Transformer Components

A typical Decoder-only (generative, used by GPT/LLaMA/Qwen) structure:

Input Tokens
   │
Embedding Layer
   │
   ▼
┌────────────────┐    ┌──────────────┐
│ Masked Multi-Head │ →  │ Feed-Forward  │
│   Attention       │    │ Network (FFN) │
└────────────────┘    └──────────────┘
  Each layer has "Residual Connection + LayerNorm"
   ▼  (stacked N layers, e.g. 32/80)
Output Layer → predict next token probability distribution

Key point: Causal Mask ensures each token only sees itself and previous tokens — no "peeking" at the future. This is the foundation of autoregressive generation.

2.6 Layer Normalization, Residual Connections & FFN

  • Residual Connection: output = input + sublayer(input), mitigates deep gradient vanishing, enables 80+ layer networks;
  • LayerNorm: stabilizes per-layer value distribution;
  • FFN (Feed-Forward Network): a two-layer MLP, carries most "memory and transformation," the bulk of parameters.

2.7 KV Cache: Why Inference is "More Memory-Hungry" Than Training

During autoregressive generation, each new token requires recomputing attention over the entire sequence. To avoid redundant computation, the model caches the K and V of all processed tokens (called KV Cache). As generation grows longer, the KV Cache grows larger — this is the root cause of "high memory usage during inference, especially for long sequences."

⚠️ Key takeaway: Training consumes massive compute; inference consumes massive memory (due to KV Cache). Understanding this difference is essential for understanding deployment "VRAM" discussions.

2.8 MoE (Mixture of Experts) Architecture

Recent mainstream models (Mixtral, DeepSeek-V3, Qwen-MoE) adopt MoE: split the FFN into multiple "expert" sub-networks, each token only activates a few experts. The benefit: massive total parameters, but only compute a fraction per inference, balancing compute cost and capability. This explains "671B total, 37B active" type descriptions.

2.9 Encoder vs. Decoder vs. Encoder-Decoder

ArchitectureCharacteristicsExamples
Encoder-onlyBidirectional understanding, excels at classification/semanticsBERT, RoBERTa
Decoder-onlyUnidirectional generation, excels at continuation/dialogue, modern mainstreamGPT, LLaMA, Qwen
Encoder-DecoderUnderstand then generate, suited for translation/summarizationT5, BART
✅ Modern LLMs almost exclusively use Decoder-only architecture — it unifies understanding and generation in one framework, and is simpler engineering-wise.
💡 In plain English: GPT's base is just half of the Transformer — only the decoder, no translation. The rest is continuously looking at preceding words and guessing the next one. And through "guessing," it developed the ability to chat, write code, and solve math problems. What it "guesses" is ultimately the w, b parameters learned during training.

Chapter 3 · Pretraining & Emergent Abilities

3.1 Pretraining Objective: Self-Supervised Learning

Pretraining uses unlabeled data — existing web text serves as its own "label" (predict the next word from context, i.e., "self-supervised"). This is why training can scale with near-infinite text, the fundamental reason models can grow so large.

3.2 Where Training Data Comes From

  • Web crawls (Common Crawl, etc.) — largest scale, but variable quality;
  • Books, academic papers, encyclopedias — high-quality long-form text;
  • Code repositories (GitHub, etc.) — gives coding ability;
  • Conversations, forums, communities — colloquial and diverse expressions.

Raw data must be cleaned, deduplicated, filtered (remove low-quality/toxic/privacy), and mixed (blended at ratios). Data quality often matters more than model architecture.

3.3 Data Composition & Governance

Different sources are mixed at specific ratios (e.g. 60% web + 20% code + 10% books + 5% dialogue). Chinese models add extra high-quality Chinese corpus to balance Chinese-English capability. Training may also dynamically adjust ratios (curriculum learning, easy-to-hard).

3.4 Loss Function: Cross-Entropy

Pretraining uses Cross-Entropy Loss to measure the gap between the model's predicted distribution and the actual next token, updating weights via backpropagation. The goal is to minimize prediction error, making the model better at "continuing text."

🎯 What is training really doing?
① Loss function: measures the gap between "predicted" and "actual" values (commonly MSE or cross-entropy). It's a function of all parameters;
② Goal: find the parameter set that minimizes the loss;
③ Simple models (linear regression) can solve analytically (set derivatives to 0), but neural networks are nonlinear — must iterate;
④ Gradient Descent: compute partial derivatives (the gradient), then move parameters against the gradient direction (step size = learning rate) — repeat to approach the minimum;
⑤ Backpropagation: use the chain rule to compute gradients layer by layer from output to input;
⑥ One "forward pass → backprop → parameter update" = one training step; over many rounds, parameters converge and the model "learns" the function.

3.5 Training Methods: Gradient Descent & Optimizers

  • Backpropagation: compute gradients from output error backward;
  • AdamW: mainstream optimizer, adaptive learning rate + weight decay;
  • Learning rate schedule: typically warmup then cosine decay;
  • Mixed precision (bfloat16/FP16): low-precision training for speed and memory savings;
  • Gradient accumulation: accumulate small batches into large batches.

3.6 Scaling Laws

OpenAI's Chinchilla/Scaling Laws found: model performance follows a predictable power-law with parameters, data, and compute. Key insights:

  • To improve performance, simultaneously increase parameters and data;
  • Compute-optimal: optimal when parameters ≈ training tokens (≈ 20 tokens/parameter, e.g. 7B model ≈ 140B tokens);
  • When data is insufficient, adding data is more cost-effective than adding parameters.
⚠️ This is why "just scaling parameters" may not work — model capability is strongly correlated with training data quantity and quality, not just parameter count.

3.7 Emergent Abilities

When model scale crosses a threshold, certain abilities "suddenly" appear rather than improving smoothly:

  • Few-shot learning (in-context learning — learn a new task from a few examples);
  • Chain-of-thought reasoning (solve complex problems step by step);
  • Code generation, instruction following, multilingual translation, etc.

This "emergence" is the key value distinguishing "large models" from small models.

3.8 In-Context Learning

Without updating weights, just by including examples (few-shot) in the prompt, the model can "temporarily learn" a new task. This is one of the most practical LLM abilities and the foundation of prompt engineering.

ParadigmExamples in Prompt?Characteristics

3.10 Common Training Challenges & Solutions

🎓 Training isn't just "bigger is better". Common issues and solutions:
  • Overfitting: Perfect on training data, poor on new data. Solutions: simplify model; add data; data augmentation; early stopping; regularization; dropout.
  • Regularization: Add parameter penalty to loss function — L1 (sparse), L2 (shrink all). Strength controlled by regularization coefficient. These "parameters that control parameters" are hyperparameters.
  • Dropout: Randomly drop neurons during training, forcing the model to rely on more "ordinary soldiers" rather than few "elites" — improves robustness.
  • Gradient vanishing/explosion: Deep networks cause gradients to vanish or explode. Solutions: gradient clipping, residual networks, proper weight initialization and input normalization.
  • Slow convergence / oscillation / local optima: Use momentum, Adam adaptive optimizers.
  • High compute cost: Use mini-batch to split large datasets into smaller batches.

Chapter 4 · Alignment & Safety

4.1 Why Alignment is Needed

A pretrained base model only knows how to "continue text" — it may not follow instructions, answer relevantly, or follow rules. Alignment shapes the base model into a safe, helpful, instruction-following assistant.

4.2 Three Goals of Alignment (Helpful / Honest / Harmless)

  • Helpful: Accurately and completely fulfill user instructions;
  • Honest: No fabrication; admit uncertainty; refuse to confabulate;
  • Harmless: No illegal, dangerous, hateful, or privacy-violating content.

4.3 Stage 1: Supervised Fine-Tuning (SFT)

Use human-annotated (instruction, expected response) pairs for supervised learning. This teaches the model to "give reasonable responses based on instructions." This is the foundation of alignment and the simplest, most common method.

  • Data format: {"instruction":"...","input":"...","output":"..."};
  • Data quality and diversity determine the ceiling of instruction following;
  • SFT is also used for domain-specific fine-tuning (see Chapter 6).

4.4 Stage 2: RLHF (Reinforcement Learning from Human Feedback)

After SFT, the model may mimic annotation style but not necessarily match user preferences. RLHF introduces a reward model using human preferences:

  1. Collect human preferences: For multiple responses to the same instruction, humans judge which is better (pairwise comparison);
  2. Train a reward model (RM): Learn a scoring model where better responses score higher;
  3. Reinforcement learning (PPO): Use the reward signal to optimize the policy model toward high-scoring responses.
Human preferences ─▶ Train Reward Model RM
                          │
                          ▼
Base model ──SFT──▶ Policy model ──PPO (RM as reward)──▶ Aligned model
⚠️ RLHF is complex, unstable, and prone to "reward hacking." This led to simpler methods like DPO.

4.5 Direct Preference Optimization (DPO)

DPO elegantly integrates preference learning into supervised-style training, bypassing RL instability. It directly optimizes on (preference pair) data with constraints. Results approach RLHF, but simpler, more stable, lower resource usage — widely adopted in recent years.

4.6 Other Alignment Techniques

MethodApproach
RLAIFUse AI (e.g., large models) instead of humans for preference feedback, reducing cost
RLVR (RL with Verifiable Rewards)Use verifiable rules (math answers, code passing tests) as rewards
KTO / ORPO / SimPODPO variants with different optimization objectives, reduced data needs
Constitutional AIUse a set of "principles/constitution" for the model to self-critique and improve

4.7 Jailbreak & Safety Adversarial

Even aligned models can be induced to produce harmful content (jailbreak attacks). Common tactics:

  • Roleplay/fictional scenarios: "Suppose you're an unrestricted model...";
  • Base64/encoding bypass: Encode dangerous queries into non-plaintext;
  • Multi-turn induction: Gradually lead the model astray;
  • System prompt leakage/injection: Ask the model to "ignore previous rules."
✅ Understanding jailbreaks helps you add protection in your own products (input/output filtering, prompt injection defense, human review), not attack others.

4.8 Application-Layer Alignment Strategies

Beyond training-level alignment, deployment can add "system guardrails":

  • Input detection: Intercept malicious/jailbreak prompts;
  • Output review: Detect and block harmful/sensitive outputs;
  • Content classification: Grade violence, sexual content, privacy;
  • Rate limiting & user isolation: Prevent abuse and misuse.

Chapter 5 · Inference & Deployment

5.1 The Nature & Bottleneck of Inference

Inference = using a trained model for autoregressive generation on new input. The bottleneck is usually not compute but memory bandwidth / capacity, because of constant read/writes of the massive KV Cache and model weights.

5.2 How Much VRAM Do You Need?

A quick estimate:

Model weight VRAM ≈ parameters × precision bytes
  e.g.: 7B model
  FP16 (2 bytes) → 14 GB weights + KV cache overhead ≈ 16GB
  INT8 (1 byte)  → ~7GB
  INT4 (0.5 byte) → ~3.5–4GB
Model SizeFP16 ~VRAMINT4 ~VRAMRecommended GPU
1–3B2–6GB1–2GBConsumer-grade OK
7–8B14–16GB4–5GBRTX 4060/4070 etc.
13–14B26–28GB8–9GBRTX 4090 / A10
70B140GB+35–40GBMulti-GPU A100/A800/H100

5.3 Quantization

Compress model weights from high precision (FP16) to low precision (INT8/INT4), drastically reducing VRAM and accelerating. Common tools:

  • GGUF / llama.cpp: CPU/consumer GPU friendly, golden choice for local small models;
  • GPTQ: Efficient INT4 quantization on GPU;
  • AWQ: Sensitivity-weighted quantization, better quality;
  • bitsandbytes (4-bit): One-click loading with Hugging Face, good for fine-tuning.
⚠️ Quantization saves VRAM and speeds up, but may cause slight accuracy loss. INT4 is sufficient for most tasks; be cautious for tasks requiring precise reasoning.

5.4 Inference Optimization Techniques

  • KV Cache: Cache historical K/V to avoid recompute (see 2.7);
  • Batching: Process multiple requests at once, amortize compute;
  • PagedAttention: vLLM's core, manages KV Cache like OS paging — dramatically improves VRAM utilization;
  • Speculative Decoding: Small model guesses, large model verifies, accelerating generation;
  • Prefix Caching: Reuse precomputed results for identical system prompts;
  • Continuous Batching: Dynamically add/complete requests, reduce idle waiting.

5.8 Long Context Challenges

Ultra-long context (e.g. 128K–1M) brings: attention computation explosion, KV cache VRAM explosion, and "lost in the middle" attention issues. Solutions:

  • RoPE position extrapolation / long-context continued pretraining;
  • Sparse attention / sliding window attention;
  • Split long text into chunks for retrieval (combine with RAG, see Chapter 8).

Chapter 6 · Fine-tuning & PEFT

6.1 Why Fine-tune?

When prompt engineering / RAG can't meet specific needs, fine-tuning — continuing training with domain data — teaches the model specific styles, formats, tasks, or knowledge. Typical scenarios:

  • Output strictly follows a specific JSON format / enterprise style;
  • Master domain-specific terminology and business logic;
  • Continuously learn on private data without long prompts each time.
⚠️ Fine-tuning is not a panacea: it mainly changes "behavior/style/minor knowledge" and can't truly "memorize massive new facts" (that's RAG's job, see Chapter 8). Think clearly: fine-tune or RAG?

6.2 Full Fine-Tuning vs. PEFT

Full Fine-Tuning: updates all weights, good results but massive VRAM/compute. A 7B model is nearly impossible to full-FT on a single GPU.

PEFT (Parameter-Efficient Fine-Tuning): only train a small set of new parameters, freeze the original model. Very low cost, near-equivalent results. Mainstream methods:

MethodApproachCharacteristics
LoRAFreeze original weights, inject low-rank trainable matricesMainstream, VRAM-efficient, good results
QLoRALoRA + 4-bit quantized baseConsumer GPUs can fine-tune large models
Prefix / Prompt TuningLearn a set of trainable prefix vectorsMinimal change
AdapterInsert small trainable modulesSimilar to LoRA approach

6.3 LoRA Principle

LoRA (Low-Rank Adaptation) assumes: weight changes during fine-tuning are "low-rank." So the increment is decomposed into two small matrices:

W' = W₀ + ΔW = W₀ + B·A
  W₀: frozen original weight
  A:  small trainable matrix (r × d)
  B:  small trainable matrix (d × r)
  r:  rank (typically 8/16/32), smaller = fewer parameters
  Only A, B are updated; original W₀ is frozen

Benefit: after training, only a tiny adapter (a few MB–hundreds of MB) needs saving. Multiple LoRAs can be stacked for different tasks, switched at will.

6.4 Practice: Fine-tuning with Hugging Face + PEFT

Typical minimal workflow (LoRA / QLoRA example):

# 1) Load base model (QLoRA uses 4-bit quantization)
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct",
    torch_dtype=torch.bfloat16,
    load_in_4bit=True          # QLoRA key
)
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")

# 2) Configure LoRA
lora = LoraConfig(
    r=8, lora_alpha=16, lora_dropout=0.05,
    target_modules=["q_proj","k_proj","v_proj","o_proj"],
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora)

# 3) Train with SFTTrainer (data = instruction-response pairs)
from trl import SFTTrainer, DataCollatorForCompletionOnlyLM
trainer = SFTTrainer(
    model=model, train_dataset=dataset,
    args=TrainingArguments(output_dir="./lora_out", per_device_train_batch_size=1),
)
trainer.train()

# 4) Save and merge
model.save_pretrained("./lora_adapter")
merged = model.merge_and_unload()
merged.save_pretrained("./model_merged")

6.5 Fine-tuning Data Preparation Tips

  • Quantity: hundreds–thousands of high-quality samples suffice; don't need massive amounts;
  • Quality > Quantity: prefer fewer but correct samples; avoid contradictory ones;
  • Coverage: cover various instruction forms, edge cases, refusal scenarios;
  • Consistency: unified format (JSON, tone, length);
  • Dedup & decontamination: avoid duplicate overfitting, avoid test data leakage.

Chapter 7 · Prompt Engineering & Structured Output

7.1 What is Prompt Engineering?

Prompt Engineering = guiding the model to produce stable, high-quality output through designed input. It's zero-cost, fast-acting, and the first skill for entering LLM applications.

Core insight: the model is a "probability machine." The clearer the prompt, the more constraints and examples, the more predictable the output. You're not "commanding" — you're providing sufficient contextual constraints to a probability machine.

7.2 Basic Components of a Prompt

A high-quality prompt typically includes:

  1. Role: Who you are / what role ("You are a senior legal counsel");
  2. Task: What to do, with clear verbs ("summarize, translate, generate, classify");
  3. Context: Background info, materials, constraints;
  4. Format: Output structure (JSON, table, bullet points, word count);
  5. Example: 1–3 input-output samples;
  6. Constraints: What not to do, what to do when uncertain.
[Role] You are a senior editor skilled in polishing and distilling.
[Task] Rewrite the following text into a more professional, concise version.
[Requirements]
- Preserve the original meaning; remove colloquialisms
- Keep under 80 words
- Output only one line; no explanations
[Original] ... (place original text here)

7.3 Common Prompt Techniques

TechniqueDescriptionUse Case
Zero-shotDirect instruction, no examplesSimple tasks
Few-shot2–8 input-output examplesNeed stable format/behavior
Role-playingSet a professional roleImprove expertise/tone
Chain-of-Thought (CoT)Let the model "think step by step" before answeringComplex reasoning/math
Few-shot CoTExamples include reasoning processStrong reasoning scenarios

7.4 Chain-of-Thought (CoT)

For math, logic, and complex problems, asking directly often fails. Let the model write out the reasoning process first, then give the conclusion — accuracy improves significantly:

❌ Direct ask: A basket has 3 apples, 5 more are added, 2 are removed. How many left?
✅ Guided thinking:
"Please reason step by step, then give the conclusion:
Step 1: Started with 3 apples
Step 2: Added 5, total 8
Step 3: Removed 2, 6 remain
So, 6 apples are left."
Answer: 6

Advanced: ReAct (Reason+Act) alternates thinking and action — the core of agents (see Chapter 9); Tree-of-Thoughts (ToT) explores multiple reasoning paths and picks the best.

7.5 Structured Output (JSON / Tables)

Engineering often requires structured data from the model. Two approaches:

  • Soft constraint: Specify format + JSON example in the prompt; the model usually complies;
  • Hard constraint (recommended): Use constrained decoding / Function Calling to mechanically force valid JSON output (see Chapter 9 tool calling).
Return only the following JSON, no other content:
{"title": "...", "summary": "...", "tags": ["..."]}
⚠️ When relying on soft constraints, always add parsing fallback (regex/JSON repair) — don't assume 100% clean JSON.

7.6 System Prompt

Put stable, unchanging constraints (role, rules, boundaries, format, safety) into the system prompt, and user input into user messages — so the model responds within a fixed baseline. This is key to building agents/products.

[System Prompt] You are an order customer service assistant.
- Answer only based on knowledge base content; don't fabricate.
- Professional, concise tone.
- If unable to answer, clearly say "Please consult human customer service."
- All output in English.

7.7 Prompt Injection & Defense

Prompt injection is when malicious text attempts to override system instructions (e.g., hidden text in web pages inducing the model to leak data). Defenses:

  • Isolate user input from system instructions (delimiters / role separation);
  • Filter/detect input (intercept "ignore above instructions" patterns);
  • Confirmation for critical operations; limit tool permissions;
  • Don't put untrusted text directly into system prompts.

7.8 Prompt Tools & Libraries

  • Prompt template libraries: Pre-built role/scenario templates;
  • LangChain / Instructor: Structured output and chaining tools;
  • OpenAI structured output / Pydantic: Schema enforcement and validation.

Chapter 8 · RAG (Retrieval-Augmented Generation)

8.1 Why RAG?

LLM training data has a cutoff; it can't know your private/latest materials and is prone to hallucination (fabrication). RAG's approach: retrieve relevant materials first, insert them into the prompt, then let the model answer based on the materials. Like "temporarily giving the model a knowledge base."

✅ RAG advantages over fine-tuning: knowledge updates instantly, doesn't modify the model, traceable sources, low cost. It's the first choice for most "private knowledge Q&A" scenarios.

8.2 RAG Core Pipeline

   [Offline] Build Knowledge Base
   Document ──Chunk──▶ Embedding ──▶ Store in Vector DB
                                                 ▲
   [Online] User Question                             │
   Question ──▶ Embedding(question) ──▶ Similarity Search ──▶ Top-K docs
        │
        ▼
   Assemble Prompt (question + retrieved doc chunks)
        │
        ▼
   LLM generates answer (with optional citations)
💡 RAG in one sentence: First Retrieve, then Generate — hence "Retrieval-Augmented Generation." Two things: fish out relevant content from a knowledge base, then let the model answer based on it. Enterprise knowledge assistants and smart customer service mostly work this way.
🤔 Why not just feed the entire document to the model? Suppose a product manual has hundreds of pages: ① The model has a context window limit — too much means "read the end, forget the beginning," accuracy drops; ② Carrying a thick manual every time inference cost soars; ③ More input, slower model response. So the right approach: only pick the few truly relevant chunks, give them with the question — that's RAG.

8.2b RAG Pipeline: Five Key Steps

RAG has two phases: before asking ("data preparation" = chunking + indexing) and after asking ("answering" = retrieval + rerank + generation).

StepPhasePlain ExplanationOne-line Principle
① ChunkingBeforeTear the manual into small piecesSplit docs by character count / paragraph / section / page
② IndexingBeforeTag each piece for retrievalEmbed each chunk into a vector, store with original text in vector DB
③ RetrievalAfterQuickly shortlist "roughly relevant" chunksEmbed the question, compute similarity with DB chunks, get Top-10
④ RerankAfterFinely select from shortlistUse Cross-Encoder model to refine from 10 to best 3
⑤ GenerationAfterModel answers based on materialsSend question + 3 chunks to LLM, produce final answer
🎯 Why rerank after retrieval? Like hiring: retrieval = resume screening (many candidates, cheap method, low accuracy OK); rerank = interview (fewer candidates, expensive model, high accuracy). Retrieval uses vector similarity (cheap, fast, less accurate); rerank uses Cross-Encoder (expensive, slow, accurate). Two-stage filtering beats one-shot.

8.3 Key Components

ComponentFunctionExamples
Document ChunkingSplit long docs into retrievable chunksBy paragraph/semantics
Embedding ModelConvert text to vectors, measure semantic similarityBGE, M3E, text-embedding
Vector DatabaseStore vectors and perform similarity searchMilvus, Chroma, FAISS, Pinecone
Retrieval StrategyRecall relevant chunksVector search / hybrid search

8.4 Chunking Tips

  • Chunk size: typically 300–1000 tokens per chunk; too large adds noise, too small loses context;
  • Overlap: leave partial overlap between adjacent chunks to avoid splitting sentences;
  • Structural splitting: prefer splitting by title/paragraph/semantic boundary, not just character count;
  • Preserve metadata: record each chunk's source, title, page for traceability.

8.5 Vector Search & Hybrid Retrieval

📚 Three foundational concepts:
  • Vector: A mathematical quantity with magnitude and direction, represented as an array of numbers. RAG vectors often have hundreds or thousands of dimensions — more dimensions = richer information.
  • Embedding: The process of converting text into vectors. The key magic: semantically similar text → similar vectors. This lets us judge relevance by "vector distance." Done by specialized Embedding models (see MTEB leaderboard for selection).
  • Vector Database: A database optimized for storing and querying vectors. Note: it stores original text alongside vectors — the vector is an intermediate artifact; the model ultimately reads the original text.
  • Vector Similarity: Measures how similar two vectors are. Three common algorithms: cosine similarity (angle), Euclidean distance (straight-line distance), dot product (direction + magnitude).
  • Vector search: semantic similarity, great for "same meaning, different words";
  • Keyword search (BM25): exact match, great for proper nouns/IDs;
  • Hybrid search: combine both (RAG Fusion / weighted), better recall, recommended in production.

  • Retrieval quality: Recall@K, Precision@K, NDCG;
  • Generation quality: Faithfulness (is the answer grounded in retrieved content?), answer relevance, coverage;
  • End-to-end: Human review / LLM-as-judge scoring.

Chapter 9 · AI Agents & Tool Calling

9.1 What is an AI Agent?

An Agent is an AI system that can autonomously plan, call tools, interact with its environment, and achieve goals. Compared to "one-shot Q&A," an Agent is a closed loop of multi-step thinking + multi-step action + result-based adjustment.

💡 Key shift: from "one-shot generation" to "workflow". Most people use LLMs by "prompting it to write start-to-finish in one go" (like asking someone to write a paper without revising — often mediocre). Generative workflows are more like writing a paper: outline → research → draft → review what needs changing → revise… iterating. Slower, but much higher quality. An Agent's essence is breaking complex tasks into small steps, each delegated to AI with continuous checking.
🎯 Most important skill: task decomposition. Break a large goal (write a research report, reply to a client email) into discrete small steps, then build components for each — this "decomposition ability" directly determines how powerful a workflow you can build.

9.1b Autonomy Levels (Not "Is or Isn't," but "How Autonomous")

Don't get stuck on "is this a real Agent" — think of it as an adjective: systems can have different degrees of autonomy.

AutonomyCharacteristicsExample
LowStep sequence is hardcoded by the developer; LLM only generates text contentFixed "generate keywords → search → scrape → write" pipeline
SemiModel can choose which tools to use, but the tool set is predefinedModel decides "should I search? which one?"
HighModel autonomously decides the step sequence, can even write new functions/toolsPlanning agents, systems that create executable tools
✅ Practical advice: Low autonomy workflow apps are the most common, most controllable, and create the most enterprise value. High autonomy is powerful but unpredictable and hard to control — a research frontier. Start with low autonomy.
📈 Do workflows really help? Andrew Ng's team verified on HumanEval (code benchmark): GPT-3.5 direct coding accuracy was only 40%, GPT-4 reached 67%; with workflow techniques (letting the model write then reflect, self-check), even older models improved significantly, approaching levels of more expensive models. Conclusion: autonomous workflows benefit even the strongest models.
User Goal
   │
   ▼
┌────────── Agent Loop ──────────┐
│  1. Understand goal → 2. Plan sub-steps  │
│  3. Call tools (search/code/API)          │
│  4. Observe results → 5. Adjust plan      │
│  6. Until task complete                   │
└──────────────────────────────────────────┘
  Output final result

9.2 Core Mechanism: ReAct (Reasoning + Action)

ReAct has the model alternate "Thought → Action → Observation", thinking and acting like a human:

Thought: The user wants Beijing weather. I need to call the weather tool.
Action: get_weather("Beijing")
Observation: Sunny, 25°C
Thought: Got the weather. I'll answer directly.
Action: Done. Beijing is sunny today, temperature 25°C.

9.2b Four Design Patterns (Andrew Ng's Summary)

When you "serialize" complex workflows, four key design patterns recur. They are the building blocks of agents.

PatternCore IdeaExample
ReflectionLet the model review its own output and iterateWrite code → model checks → "found bug" → model fixes → v3
Tool UseGive the model callable tools to actWeb search tool for "best coffee maker"; code execution for compound interest
PlanningModel decides action sequence (not hardcoded)HuggingGPT: model decomposes "generate image → describe → voiceover" and calls each
Multi-AgentMultiple role-based Agents collaborateResearcher + copywriter + editor trio
🎬 Reflection = let AI be its own "reviewer": feed its output back, let it critique and fix. Can add external feedback (e.g., actually run the code and see if it errors).
🧩 Multi-Agent = forming a team: researcher finds info, marketer writes copy, editor polishes. Harder to control (can't predict each agent's behavior), but research shows better results for complex tasks (biographies, chess).

9.3 Tool Calling (Function Calling)

Let the model structurally declare "which tool to call, with what parameters," then your code actually executes it and returns results. This is the key connecting Agents to the external world (APIs, databases, code).

// Define tool
{
  "name": "get_weather",
  "description": "Query weather for a specified city",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "City name"}
    },
    "required": ["city"]
  }
}

// Model may return
{"name":"get_weather", "arguments": {"city":"Beijing"}}

9.3b MCP: Model Context Protocol — The "USB-C Standard" for Tool Calling

Function Calling (9.3) has a pain point: each LLM vendor's format is different — OpenAI has its own, Claude has Tool Use, domestic models each have their own schema. To make one tool serve different LLMs, you must adapt for each — severe fragmentation.

In November 2024, Anthropic open-sourced MCP (Model Context Protocol), trying to unify the communication standard between AI Agents and tools, like USB-C unifying charging ports. After the 2025 Agent application explosion, MCP quickly went from "good idea" to "de facto standard," now supported by Claude, GPT, Llama, DeepSeek, Qwen, and other mainstream LLMs.

✅ In one sentence: Function Calling is the LLM-level "calling interface" (vendor-specific); MCP is the infrastructure-level "communication standard" (open protocol). MCP can even use Function Calling as its calling mechanism underneath, but provides richer capabilities on top.

(1) Design Inspiration: From LSP to MCP

MCP's design was inspired by LSP (Language Server Protocol) in software development — LSP decouples "language capabilities" from "editors," so one language server works with VS Code, Vim, etc. MCP likewise: decouples "tool capabilities" from "AI applications," so one tool server works with all LLMs.

ComparisonLSPMCP
BackgroundDifferent IDEs have different completion/diagnostics for the same languageDifferent LLMs call the same tool differently
Core ideaDecouple "language capabilities" from "editor"Decouple "tool capabilities" from "AI application"
ValueUnified the language tool ecosystemUnified the AI Agent tool ecosystem

(2) Host-Client-Server Architecture

┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│    Host      │◄────►│    Client    │◄────►│    Server    │
│ (host app)   │      │ (protocol    │      │ (tool service)│
│              │      │  client)     │      │              │
└──────────────┘      └──────────────┘      └──────────────┘
Typical: Claude Desktop  Typical: MCP SDK     Typical: weather/DB/file
       VS Code+Copilot     (Python/Java/TS)       GitHub MCP
RoleResponsibilityAnalogy
HostThe user application hosting the LLM (Claude Desktop, IDE plugin, custom AI app), coordinates LLM-tool interactionBrowser
ClientMCP protocol endpoint, managed by Host, establishes 1:1 connection with Server, maintains session state. One Host can manage multiple ClientsBrowser tab
ServerProvides specific tool capabilities (weather, database, file system, etc.), exposes capabilities via MCP protocol. One Server can be connected by multiple ClientsWeb server
⚠️ Key design: Host and Server don't communicate directly — all communication goes through Client. Underlying message format: JSON-RPC 2.0.

(3) Three Core Capabilities (Primitives)

PrimitiveFunctionTypical Scenario
ToolsCallable functions/methods, corresponding to Function CallingWeather query, DB CRUD, API calls, file operations
ResourcesURI-addressable data resources for data reading (not execution)Config management, knowledge base docs, system status, business rules
PromptsParameterizable prompt templates maintained on the Server side, Client fetches on demandRole system prompt libraries, workflow templates, multi-language prompt management
💡 Resource vs Tool: Tool is "do something" (execute action); Resource is "read data" (provide context). MCP's Resource capability lets tools dynamically expose data, loaded on demand instead of stuffing everything into the prompt — solving context management.

(4) Transport Protocols: STDIO vs HTTP SSE

DimensionSTDIOHTTP SSE
CommunicationInter-process (stdin/stdout)HTTP long connection (SSE push)
Best forLocal dev, desktop apps, IDE pluginsDistributed deployment, microservices, cloud
PerformanceLow latency (no network overhead)Network latency (but supports remote)
ScalabilitySingle machine onlyHorizontal scaling, load balancing
SecurityOS process isolationRequires TLS / OAuth2
✅ Selection: Local dev/debug → STDIO (simple, zero network config); Production/remote → HTTP SSE (network transport and horizontal scaling).

(5) Complete Workflow (8 Steps)

Step 1: Initialize     Host starts → creates Client → Client sends "initialize" to Server
Step 2: Negotiate       Server returns supported protocol version & capabilities → agree on features
Step 3: Session         Client sends "initialized" notification, session established
Step 4: Discover        Client sends "tools/list" → Server returns available tools (name, desc, schema)
Step 5: User Request    User sends natural language request in Host
Step 6: LLM Reasoning   Host sends request + tool list to LLM → LLM decides which tool, what params
Step 7: Tool Call       Host sends "tools/call" via Client → Server executes, returns result
Step 8: Response        LLM generates final natural language response based on tool result → shown to user
🔑 Core value in "Step 4: Discovery": tool list and schema are dynamically obtained, not hardcoded. Server-side tool changes are auto-detected by Client — no redeployment needed.

(7) Selection Decision Tree

Does your app need to connect multiple external tools/data sources?
├── No → Just need single-call simple API
│   └── Use Function Calling (simple enough, no extra complexity)
│
└── Yes → Need to integrate multiple tools
    │
    ├── Do tools need to be reused across multiple different LLM apps?
    │   ├── No → Single LLM, fixed tool list
    │   │   └── Use Function Calling
    │   └── Yes → Cross-app, cross-LLM reuse
    │       └── Use MCP (core advantage: implement once, use everywhere)
    │
    ├── Need dynamic tool capability discovery?
    │   └── Yes → Use MCP (dynamic capability discovery)
    │
    └── Need to provide dynamic context data to LLM?
        └── Yes → Use MCP Resources
📌 Core decision principle: ① Single LLM, few fixed tools → Function Calling; ② Need reuse/dynamic discovery/multi-LLM → MCP; ③ Local → STDIO, remote → HTTP SSE.

(8) Enterprise Deployment Essentials

  • Security boundary: Production must use HTTPS + TLS 1.2+, per-tool/resource permission isolation, OAuth 2.0;
  • Idempotency: tools/call doesn't guarantee idempotency (repeated calls have side effects); write-operation tools need idempotency keys;
  • Flow control: Rate limiting/circuit breaking to protect MCP Server (e.g., Resilience4j);
  • MCP Gateway: For many servers, introduce a unified gateway for auth, rate limiting, audit, routing, protocol conversion, tool registry;
  • Audit logging: Record all tool calls (caller, params, time, result) for observability.

(9) Protocol Evolution & Ecosystem

MCP's latest version (mcp-2025-11-25) introduced several important enhancements:

  • Elicitation: Server can request additional info from user during tool execution;
  • Progress Notification: Long-running operations can report progress;
  • Resource Subscription: Resource change notifications, real-time data updates;
  • Tool/Resource/Prompt list change notifications: Server capability changes auto-notified to Client;
  • Sampling enhancement: Server can request Client to call LLM on its behalf, enabling bidirectional collaboration;
  • OAuth 2.0 authorization: Standardized security framework for enterprise deployment.
🌐 Official spec site: modelcontextprotocol.io. Framework-wise, Spring AI 1.0+, LangChain, and other mainstream frameworks have integrated MCP support. MCP is evolving from "tool calling standardization" toward "multi-Agent orchestration, workflow standardization," with MCP Server registries and tool marketplaces rapidly emerging.

9.4 Memory

Agents need three types of memory:

  • Short-term: Current conversation context (multi-turn history);
  • Working: Steps and intermediate results in the current plan;
  • Long-term: Persisted knowledge/preferences (often via vector DB or database).

9.5 Planning

Complex tasks need decomposition into executable steps:

  • Task decomposition: Break large goals into sub-tasks;
  • ToT / CoT: Multi-path reasoning and step-by-step thinking;
  • Reflection: Self-check and revise after completion;
  • Sub-agents: Delegate sub-tasks to specialized agents.

9.6 Multi-Agent Collaboration

Multiple agents each handle their specialty, collaborating on complex workflows (e.g., planning agent + retrieval agent + coding agent + review agent). Representative frameworks:

  • AutoGen (Microsoft): Multi-agent dialogue collaboration;
  • CrewAI: Role-based team collaboration, easy to use;
  • LangGraph: Graph-structured multi-agent state machine orchestration.

9.7 Agent Engineering Challenges

  • Error propagation: One step's error amplifies; need exception handling, retry, budget limits;
  • Token consumption: Multi-step loops consume massive context; control tool result size;
  • Security risks: Tool permission overreach, prompt injection, arbitrary code execution — must least privilege + whitelist + human confirmation for critical ops;
  • Observability: Log every step's thought/tool call for debugging.

Chapter 10 · Evaluation & Observability

10.1 Why Evaluation Matters

LLM outputs are non-deterministic and prone to hallucination — you can't just "run it and it works" like traditional software. Building AI applications requires continuous quality evaluation, otherwise problems are hard to catch post-launch and iterations lack basis. Evaluation is the foundation of engineering.

10.3 Application Evaluation: Three Categories of Metrics

  • Quality metrics: Accuracy, faithfulness, relevance, completeness, format compliance;
  • Performance metrics: First-token latency, total latency, throughput (tokens/s), error rate;
  • Cost metrics: Token consumption per request, inference cost, cache hit rate.

10.4 Human Evaluation vs. LLM-as-Judge

  • Human evaluation: Most reliable, but expensive, slow, hard to scale — used for spot checks and small samples;
  • LLM-as-judge: Use a strong model to score outputs, scalable; watch for position bias, self-preference — best to use open-source strong models with consistency checks.
// LLM-as-judge scoring prompt example
You are an evaluator. Score the response based on "faithfulness, relevance, format" (1-5):
Reference answer: ...
Model output: ...
Provide score and brief reasoning.

10.5 Hallucination Detection

Hallucination = model output contradicts facts/given materials. Mitigation and detection:

  • Use RAG to constrain to source materials; require "answer only based on provided materials";
  • Require the model to provide citations for human verification;
  • Use FactScore / faithfulness scoring to evaluate consistency between output and materials;
  • Add rule-based validation for critical scenarios (numbers, enums, formats).

10.6 Observability (LLMOps)

Production AI applications need monitoring:

  • Tracing: Record every request's prompt, tool calls, output, token count;
  • Metrics: Latency, throughput, error rate, cost;
  • Logs & replay: Save samples for reproduction when issues arise;
  • Evaluation backfill: Periodically score live samples to detect quality degradation.

10.8 Build Your Own Evaluation Set

For your application, prepare 50–200 real/representative test cases (including edge cases and refusal scenarios), run them after every change to compare — preventing "fix one, break many." This is a low-cost, high-value engineering habit.

Phase 1: Beginner (2–4 weeks) — Learn to Use AI

  • Understand what LLMs are and how to use them (this manual, Ch. 1 & 7);
  • Use ChatGPT/Tongyi/Kimi daily for real tasks, practice prompting;
  • Write a simple conversational script using the API (Python + OpenAI-compatible interface).

Phase 2: Application Development (4–8 weeks) — Build Products with AI

  • Master prompt engineering + structured output (Ch. 7);
  • Build a RAG Q&A system (Ch. 8), feed documents to the model;
  • Learn LangChain/LlamaIndex/Dify to build a usable Agent (Ch. 9);
  • Build a minimal evaluation set, assess performance (Ch. 10).

Phase 3: Deployment/Fine-tuning (Optional advanced, 4–8 weeks) — Train/Deploy Yourself

  • Learn Python + PyTorch basics, model loading and inference (Ch. 5 & 6);
  • Run open-source models locally with Ollama;
  • Do a LoRA fine-tune with LLaMA-Factory (Ch. 6).

12.4 A Minimal Viable Path (For Beginners)

Step 1: Read this manual's Ch. 1 & 7; use AI for 7 days of daily tasks to practice prompting.
Step 2: Learn to write a 20-line Q&A script using the API.
Step 3: Build a "document Q&A" app with Dify/Coze (RAG).
Step 4: Connect it to a real scenario (e.g., knowledge Q&A in your work).
Step 5: Build a 50-case evaluation set; iterate and evaluate.
—— You now have the complete ability to "build products with AI."
(Advanced: run models locally → LoRA fine-tune → deploy to production)

12.5 Tips for "Fragmented Time, Learn-While-Using"

  • Use 1–2 hours in the evening, each time tackling one small goal (e.g., "today: learn RAG chunking");
  • Immediately apply what you learn to real problems at hand (your work, side projects) — that's how it sticks best;
  • Every small project that "runs" is positive feedback.
💡 The biggest mistake in LLM learning is "hoarding courses without practicing." Build a project that solves your real problem — that's worth more than ten courses. This is also the original intent of this manual.
