第 1 章 · 基础概念与工作原理

1.1 什么是大语言模型（LLM）

大语言模型（Large Language Model, LLM）是一类基于深度神经网络、在海量文本上训练的统计模型，核心任务是预测下一个 Token。它本身并不"理解"世界，而是学会了一种极其强大的文本概率分布——给定前文，预测下一个最可能出现的字/词。

正因为训练数据几乎覆盖了人类书写的绝大部分知识，模型学会了语法、逻辑、常识、代码、甚至推理的"模式"。当你输入一句话，它实际上是在逐 token 地、基于上下文概率，把一个合理的回答"生成"出来。

1.2 关键术语

术语含义
Token（词元）模型处理的最小文本单位，可以是词、子词或字符。中文通常一个汉字约 1 个 token，英文一个词约 1.3 个 token。
上下文窗口（Context Window）模型一次能"看到"的输入 + 输出的总 token 上限，如 8K / 128K / 1M。
参数（Parameters）模型内部的权重数量，如 7B=70 亿参数、70B=700 亿参数。参数越多通常能力越强。
预训练（Pretraining）在海量无标注文本上学习语言规律的阶段，产出"基座模型"。
对齐（Alignment）让模型遵循人类指令、符合人类偏好与安全要求的训练阶段。
推理（Inference）用训练好的模型对新输入做预测（即"生成回答"）的过程。
生成式 vs 判别式LLM 属于生成式模型，能"创造"新内容，而不只是分类判断。
温度（Temperature）控制输出的随机性。低温度更确定，高温度更多样。
Top-p / Top-k采样策略，限制从概率最高的前 k 个或累计概率 top-p 的 token 中抽取。
✅ 最小认知：LLM = "一个超大的、读过几乎所有文字的概率模型，逐字把最合理的回答写出来"。抓住这一点，后面所有概念都能串起来。

1.3 为什么"预测下一个词"能产生智能

这是最反直觉也最重要的一点：一个只是"预测下一个词"的模型，怎么会写代码、推理、翻译？答案是：为了预测下一个词，模型必须内在地学会语法、逻辑、常识、知识关联，甚至某种程度的推理。就像一个人为了接上一句话，往往需要真正理解上一句。

当训练数据达到海量规模、模型参数达到百亿级以上，就会出现所谓涌现能力（Emergent Abilities）——某些能力在模型规模达到某阈值后"突然"出现，而非平滑提升。例如少样本学习、代码生成、多步推理等。

1.4 自回归生成：如何"逐词输出"

LLM 生成文本是自回归（Autoregressive）过程：

  1. 输入 user prompt，模型预测第一个 token 的概率分布；
  2. 按采样策略（temperature / top-p）挑一个 token；
  3. 把新 token 拼回上下文，再次预测下一个；
  4. 重复，直到遇到结束符或达到最大长度。
输入:  "中国的首都是"
Step1:  P(北京)=0.82  P(上海)=0.10  P(南京)=0.05 ...
取 token → "北京"
输入:  "中国的首都是北京"
Step2:  P(。)=0.95  P(。！)=... → 取 "。"
...
最终:  "中国的首都是北京。"

1.5 生成方式：一次性 vs 流式

实际使用中，模型可以一次性输出完整回答，也可以流式（Streaming）逐 token 返回（打字机效果），后者的首 token 延迟更低、体验更好，是 Chat 产品的标配。

典型的现代 LLM 生产流程是"基座模型 + 对齐 + 微调"三段式：

海量文本 ──预训练──▶ 基座模型(Base)
                         │
                         ▼
指令数据 ──监督微调(SFT)──▶ 会听话的模型
                         │
                         ▼
人类偏好  ──RLHF/DPO──▶ 对齐模型(满足偏好与安全)

特定任务数据 ──微调/LoRA──▶ 垂直/专用模型
🧩 一句话串起全部概念（据「飞天闪客·速览大模型 100 词」整理）：
万物皆函数 → 早期想写出精确函数（符号主义）碰壁 → 转为先搭一个复杂函数（=模型）、再按"预测与真实误差"反复调参数（=权重）（连接主义）。参数海量就叫大模型，用于文字的就是大语言模型；
调参数 = 训练，先在海量文本上跑 = 预训练，再针对具体任务练 = 微调；参数定好后用函数算输出 = 推理；
参数量大到一定程度，突然冒出之前没有的能力 = 涌现；
只给服务不给代码/权重 = 闭源（GPT/Claude/Gemini）；开放权重可下载部署 = 开源模型（DeepSeek、LLaMA，更准确叫"开放权重"）；下载到本地用 = 私有化部署。
用它时：每个最小文字单位叫 Token，你给它的全部信息叫 上下文 / 提示词（Prompt）；控制随机性的参数叫 温度、采样叫 Top-k；它一本正经胡说叫 幻觉，解决办法是先联网查资料（联网）或到私有知识库查（RAG）；多步编排叫 工作流，封装成能自动干一类活的是 智能体（Agent），多个协作是 多智能体，给 AI 统一操作外部世界的接口是 MCP。

1.7 中文模型与 Tokenizer

中文的 token 切分与英文不同。一个好的 tokenizer 会尽量把常用字词合并成单个 token，减少序列长度、提高效率。这也是为什么不同模型对同一段中文的 token 消耗不同。

文本片段大致 token 数
"你好世界"约 1~2 个 token
一句中文（20字）约 10~18 个 token
一页中文文档（约500字）约 300~450 个 token
💡 记住：你是在跟"一台巨大的概率机"对话，而非"一个有意识的实体"。理解这一点，能帮你更理性地设计提示词、评估输出。

第 2 章 · 模型架构：Transformer 与注意力

🎬 直觉先行（据 B 站「飞天闪客·一小时从函数到 Transformer」整理）：别急着记公式，先抓住这条发展主线——
① 世界万物都可看成函数（早期"符号主义"想直接写出精确函数，但人类写不出"识别猫"这种函数）→ 转向连接主义：承认找不到精确解，只求足够接近的近似解；
② 用一条直线（y = wx+b）去猜近似关系，靠反复调 w、b 逼近 → 直线太"死"，于是在外面再套一层激活函数（平方/sin 等）让它"变弯"，并可以无限套娃组成复杂函数；
③ 把这种"线性变换 + 激活函数"的套娃画成图，每个圈就是一个神经元，层层相连就是神经网络；数据从左到右算一遍叫前向传播；
④ 剩下的一切（反向传播、梯度、Transformer……）本质上都是在求那一堆 w、b（权重矩阵）等于多少。
抱着"所有模型只是在猜一组函数参数"的心态读下文，注意力、多头、MoE 都只是这棵树上长出的枝干。

2.1 从 RNN 到 Transformer：为什么需要注意力

先把文字变成数字（据「飞天闪客」）：计算机只能处理数字，所以每个词都要编码成向量。太简单的编号（一个词一个数字）维度太低、丢语义；独热编码 One-hot（词表大小一个向量、只一位是 1）维度太高又稀疏，词与词之间全是正交、毫无相关性。于是有了词嵌入（Embedding）——把每个词映射成一个"不高不低"维度的向量，且用点积/余弦相似度就能算出词与词的语义远近（甚至出现"国王-男人+女人≈女王"的语义加减）。这套词向量就是送入神经网络的输入。

最初的序列模型 RNN 用隐藏状态让信息在词与词之间"接力传递"，从而具备理解先后顺序的能力。但它有两个致命缺陷：信息随时间步变长而流失（长期依赖难捕捉），且必须串行逐词处理（无法并行）。改进的 GRU/LSTM 只是"缓解"而非"根治"。

在 Transformer 之前，主流序列模型是 RNN / LSTM，它按顺序逐个处理 token，把信息压缩进一个"隐藏状态"。问题有两个：

  • 长距离依赖难：越早的信息越容易被遗忘（梯度消失/爆炸）；
  • 无法并行：必须等上一个 token 处理完才能处理下一个，训练慢。

2017 年谷歌提出 Transformer（论文 Attention Is All You Need），用自注意力机制同时解决这两点：每个 token 都能"直接看到"序列里所有其他 token，且可以并行计算。从此，注意力机制取代循环成为主流。

2.2 自注意力（Self-Attention）核心思想

对序列中的每个 token，模型生成三份向量：Q（查询 Query）、K（键 Key）、V（值 Value）。其核心逻辑是"我该关注谁，就从谁那里取信息"：

  1. 每个 token 的 Q 与所有 token 的 K 做点积，得到"关注程度"（注意力分数）；
  2. 分数做 softmax 归一化，得到权重；
  3. 用权重对所有 V 加权求和，得到该 token 的新表示。
Attention(Q,K,V) = softmax( Q·Kᵀ / √d_k ) · V

Q·Kᵀ  →  计算"谁和谁相关"的分数
/√d_k  →  缩放，防止数值过大、梯度消失
softmax → 归一化成概率权重（和为1）
·V     →  按权重融合"值"信息

2.3 多头注意力（Multi-Head Attention）

不只用一组 Q/K/V，而是拆成多个"头（Head）"，每个头在不同子空间里学不同的关系（有的抓语法、有的抓指代、有的抓语义），最后拼接起来。这样模型能同时捕捉多种层面的信息。

2.4 位置编码（Positional Encoding）

注意力本身不区分顺序（"A 看到 B"和"B 看到 A"权重一样）。要告诉模型词的先后，需要给每个位置注入位置信息。常见做法：

  • 正弦/余弦位置编码（原始 Transformer）；
  • RoPE（旋转位置编码）：把位置信息通过旋转矩阵编码进 Q/K，被主流开源模型广泛采用，对长上下文友好；
  • ALiBi：给注意力分数加上基于距离的偏置，外推能力强。

2.5 Transformer 的组成部分

一个典型的 Decoder-only（生成式，GPT/LLaMA/Qwen 等都是）结构：

输入 Token
   │
嵌入层 (Embedding)
   │
   ▼
┌────────────┐    ┌──────────────┐
│ 掩码多头注意力 │ →  │ 前馈网络 FFN   │
│ (因果/自回归) │    │ (MLP)         │
└────────────┘    └──────────────┘
  每层都有"残差连接 + LayerNorm"
   ▼  (堆叠 N 层，如 32/80 层)
输出层 → 预测下一个 token 的概率分布

关键点：因果掩码（Causal Mask）保证每个 token 只能看到自己及之前的 token，不能"偷看"未来，这是自回归生成的基础。

2.6 层归一化、残差连接与 FFN

  • 残差连接（Residual）：输出 = 输入 + 子层(输入)，缓解深层梯度消失，让 80+ 层的网络能训得动；
  • LayerNorm：稳定每层数值分布；
  • FFN（前馈网络）：一个两层 MLP，承担大量"记忆与变换"，是参数的大头。

2.7 KV Cache：为什么推理比训练"更吃内存"

自回归生成时，每个新 token 都要重新算整条序列的注意力。为了不重复计算，模型把已经算过的每个 token 的 K 和 V 缓存下来（叫 KV Cache）。随着生成变长，KV Cache 越来越大——这就是推理阶段"内存占用高、长序列尤其贵"的根源。

⚠️ 记忆要点：训练阶段消耗大量算力，推理阶段消耗大量内存（因 KV Cache）。理解这个差异，才能读懂为什么部署要谈"显存"。

2.8 MoE（混合专家）架构

近年主流模型（如 Mixtral、DeepSeek-V3、Qwen-MoE）采用 MoE：把 FFN 拆成多个"专家"子网络，每个 token 只激活少数专家。好处是总参数量巨大，但每次推理只算一部分，在算力成本与能力之间取得平衡。这就是"总参 600B，激活 37B"这类说法的由来。

2.9 编码器 vs 解码器 vs 编码-解码

架构特点代表
编码器（Encoder-only）双向理解，擅长分类/语义理解BERT、RoBERTa
解码器（Decoder-only）单向生成，擅长续写/对话，现代主流GPT、LLaMA、Qwen
编码-解码（Enc-Dec）理解后生成，适合翻译/摘要T5、BART
✅ 现代 LLM 几乎清一色采用 Decoder-only 结构，因为它在统一框架下同时具备理解和生成能力，且工程上更简单。
💡 一句人话（据「飞天闪客」）：GPT 的底层其实只是 Transformer 的一半——只保留解码器、不做翻译，剩下的就是不停看着前面的词、猜下一个词。而"猜着猜着"，就猜出了聊天、写代码、解数学题的全能本领。它猜的"下一个词"本质就是上文提到的 w、b 参数学出来的。

第 3 章 · 预训练与大模型涌现

3.1 预训练目标：自监督学习

预训练利用无需人工标注的数据——互联网上现成的文本本身就是"标签"（用前文预测后文，即"自监督"）。所以它能用近乎无限的文本训练，这是规模能做大的根本原因。

3.2 训练数据从哪里来

  • 网页爬取（Common Crawl 等）——规模最大，但质量参差；
  • 书籍、学术论文、百科——高质量长文本；
  • 代码仓库（GitHub 等）——赋予代码能力；
  • 对话、社区、论坛——口语化与多样表达；

原始数据要经过清洗、去重（Dedup）、过滤（去低质/有毒/隐私）、混比（按比例混合各类数据）。数据质量往往比模型结构更能决定最终效果。

3.3 数据配比与数据治理

不同来源数据按一定比例混合（如 60% 网页 + 20% 代码 + 10% 书籍 + 5% 对话...）。中文模型会额外引入大量高质量中文语料以平衡中英能力。训练中还可能动态调整配比（课程式数据，先易后难）。

3.4 损失函数：交叉熵

🎯 训练到底在干什么（据「飞天闪客·计算神经网络的参数」整理）：记住一个朴素的闭环——
① 损失函数（Loss）：衡量"预测值"与"真实值"差多少，就是把每个样本的误差加起来（常用均方误差 MSE 或 交叉熵）。它本身是关于所有参数的函数；
② 我们的目标：找到让损失函数最小的那组参数。
③ 简单模型（如线性回归）可令导数=0 直接解出最优参数；但神经网络是非线性叠加，解不出来，只能一点点试——
④ 梯度下降（Gradient Descent）：算损失函数对每个参数的偏导（组成梯度），然后让参数沿着梯度的反方向挪一小步（步长由学习率控制），反复迭代逼近最低点；
⑤ 反向传播（Backpropagation）：用链式法则从输出层往输入层逐层求偏导（就像算齿轮传动圈数，逐级相乘），高效算出每个参数的梯度；
⑥ 一次"前向传播算损失 + 反向传播算梯度 + 沿反方向更新参数"就是一次训练，多轮下来参数逐渐收敛，就"学"到了那个函数。

预训练用 Cross-Entropy Loss 衡量模型预测分布与真实下一个 token 的差距，反向传播更新权重。目标就是最小化预测错误，让模型越来越"会接话"。

3.5 训练方法：梯度下降与优化器

  • 反向传播（Backpropagation）：从输出误差往回计算每个权重的梯度；
  • AdamW：主流优化器，自适应学习率 + 权重衰减；
  • 学习率调度：通常先 warmup（预热）再余弦衰减；
  • 混合精度（bfloat16/FP16）：用低精度加速训练、省显存；
  • 梯度累积：小批量累积出大批量，兼顾显存与稳定性。

3.6 Scaling Law（规模法则）

OpenAI 的 Chinchilla/Scaling Laws 发现：模型性能与参数量、数据量、计算量呈可预测的幂律关系。核心启示：

  • 要提升性能，需同时增大参数 和 数据；
  • 计算最优（Compute-optimal）：参数量与训练 token 数大致相等时最优——约 20 token/参数（如 7B 模型配约 140B token 训练）；
  • 数据不足时，加数据比加参数更划算。
⚠️ 这也是为什么"刷参数"未必有效——模型能力和训练数据量、质量强相关，而非单纯堆参数量。

3.7 涌现能力（Emergent Abilities）

当模型规模跨过某个阈值，某些能力会"突然"出现而非平滑提升：

  • 少样本学习（In-context Learning，给几个例子就能学会新任务）；
  • 思维链推理（Chain-of-Thought，一步步推理解决复杂问题）；
  • 代码生成、指令遵循、多语种翻译等。

这类"涌现"正是"大模型"区别于小模型的关键价值所在。

3.8 上下文学习（In-Context Learning）

不更新权重，仅通过在提示词里放入示例（few-shot），模型就能"临时学会"一个新任务。这是大模型最实用的能力之一，也是提示词工程的根基。

范式提示词是否给示例特点
Zero-shot不给示例直接下指令，最方便但依赖指令清晰度
One-shot给 1 个示例给模型一个参考
Few-shot给 2~8 个示例显著提升稳定性，最常用

工具用途

3.10 训练中的常见困境与对策（防过拟合等）

🎓 训练不只是"越大越好"（据「飞天客·调教神经网络的方法」整理）。训练中会遇到几类经典问题及解法：
  • 过拟合（Overfitting）：在训练集上完美、在新数据上拉胯——模型把噪声也学进去了。对策：① 简化模型（神经网络不是越大越好）；② 增加训练数据量；③ 数据增强（旋转/翻转/裁剪/加噪）；④ 提前终止；⑤ 正则化；⑥ Dropout。
  • 正则化（Regularization）：往损失函数里加"参数惩罚项"，抑制参数野蛮增长——L1（参数绝对值之和，偏向稀疏）、L2（参数平方和，让参数都变小）。力度由正则化系数控制。这些"控制参数的参数"统称超参数。
  • Dropout：训练时每次随机丢弃一部分神经元，逼模型学会依赖更多"普通士兵"而非少数"精锐"，从而增强鲁棒性（Hinton 提出，"简单却极其有效"）。
  • 梯度消失 / 梯度爆炸：网络深了，反向传播梯度越传越小（消失）或猛增失控（爆炸）。对策：梯度裁剪、残差网络、合理的权重初始化与输入归一化。
  • 收敛慢 / 震荡 / 局部最优：用动量法、Adam 等自适应优化器加速收敛、减少震荡。
  • 计算开销大：用 Mini-batch 把海量数据切成小批次，降低单次开销。

第 4 章 · 对齐（Alignment）与安全

4.1 为什么需要对齐

预训练出的基座模型只会"续写"，不一定会听指令、答所问、守规矩。它可能长篇大论、可能答非所问、可能说出有害内容。对齐（Alignment）就是把基座模型"塑造"成安全、有用、遵循指令的助手。

4.2 对齐的三层目标（Helpful / Honest / Harmless）

  • Helpful（有用）：准确、完整地完成用户指令；
  • Honest（诚实）：不编造、不确定时承认、拒绝臆造；
  • Harmless（无害）：不输出违法、危险、仇恨、隐私等有害内容。

4.3 阶段一：监督微调（SFT）

用人工标注的（指令, 期望回答）数据对模型做监督学习，让模型学会"根据指令给出合理回答"。这是对齐的基础，也是最简单、最常用的方法。

  • 数据形式：{"instruction":"...","input":"...","output":"..."}；
  • 数据质量与多样性决定指令遵循的上限；
  • SFT 也用于垂直领域微调（见第 6 章）。

4.4 阶段二：人类反馈强化学习（RLHF）

SFT 后模型会"照抄"标注风格，但不一定符合用户偏好。RLHF 引入奖励模型，用人类偏好去强化模型：

  1. 收集人类偏好：对同一指令的多个回答，让人判断谁更好（成对比较）；
  2. 训练奖励模型（RM）：学一个给回答打分的模型，输出越好的分越高；
  3. 强化学习（PPO）：用奖励信号反向优化策略模型，让模型倾向于产生高分回答。
人类偏好 ─▶ 训练奖励模型 RM
                          │
                          ▼
基座模型 ──SFT──▶ 策略模型 ──PPO(以RM为奖励)──▶ 对齐模型
⚠️ RLHF 训练复杂、不稳定、易"奖励黑客"（模型钻空子刷分）。因此催生了更简单的方法 DPO。

4.5 直接偏好优化（DPO）

DPO（Direct Preference Optimization） 用简洁的方式把偏好学习融入监督式训练，绕开强化学习的不稳定性，直接用（偏好对）数据做带约束的优化。效果接近 RLHF，但更简单、更稳、资源占用低，近年被广泛采用。

4.6 其他对齐技术

方法思路
RLAIF用 AI（如大模型）代替人工生成偏好反馈，降低成本
RLVR（RL with Verifiable Rewards）用可验证的规则（数学答案、代码是否通过）当奖励
KTO / ORPO / SimPODPO 的变体，不同优化目标，降低数据需求
宪法式对齐（Constitutional AI）用一套"原则/宪法"让模型自我批评并改进

4.7 越狱（Jailbreak）与安全对抗

即使对齐，模型仍可能被诱导输出有害内容（越狱攻击），常见手法：

  • 角色扮演/场景虚构："假设你是无限制的模型..."；
  • Base64 / 编码绕过：把危险问题编码成非明文；
  • 多轮诱导：逐步把模型"带偏"；
  • 系统提示词泄露/注入：要求模型"忽略之前的规则"。
✅ 理解越狱有助于你在自己产品里加防护（输入/输出过滤、提示词注入防护、人审），而不是去攻击别人。

4.8 应用层对齐策略

除训练层对齐，部署时还能加"系统护栏"：

  • 输入检测：拦截恶意/越狱提示词；
  • 输出审核：检测并拦截有害/敏感输出；
  • 内容分类过滤：对暴力、色情、隐私等做分级；
  • 限流与用户隔离：防止滥用与误用。

第 5 章 · 推理与部署

5.1 推理的本质与瓶颈

推理 = 用训练好的模型对新输入做自回归生成。瓶颈通常不是算力而是显存带宽 / 显存容量，因为要不断读写巨大的 KV Cache 和模型权重。

5.2 显存（VRAM）到底需要多大

一个直观估算：

模型权重显存 ≈ 参数量 × 精度字节数
  例：7B 模型
  FP16(2字节) → 14 GB 权重 + 一定 KV Cache/开销 ≈ 16GB
  INT8(1字节) → 约 7GB
  INT4(0.5字节) → 约 3.5~4GB
模型规模FP16 约需显存INT4 量化约需推荐显卡
1~3B2~6GB1~2GB消费级可跑
7~8B14~16GB4~5GBRTX 4060/4070 等
13~14B26~28GB8~9GBRTX 4090 / A10
70B140GB+35~40GB多卡 A100/A800/H100

5.3 量化（Quantization）

把模型权重从高精度（FP16）压到低精度（INT8/INT4），大幅降低显存与加速。常用工具：

  • GGUF / llama.cpp：CPU/消费显卡友好，本地跑小模型的黄金选择；
  • GPTQ：GPU 上高效 INT4 量化；
  • AWQ：按重要通道做敏感度加权量化，质量更好；
  • bitsandbytes（4-bit）：配合 Hugging Face 一键加载，适合微调。
⚠️ 量化能省显存、提速，但可能带来少量精度损失。INT4 对多数任务足够，对需精确推理的任务谨慎。

5.4 推理优化技巧

  • KV Cache：缓存历史 K/V，避免重复计算（已在 2.7 讲）；
  • 批处理（Batching）：一次处理多个请求，摊薄计算、提升吞吐；
  • PagedAttention：vLLM 的核心，像操作系统分页管理 KV Cache，显存利用率大幅提升；
  • 投机解码（Speculative Decoding）：用小模型猜、大模型验，加速生成；
  • 前缀缓存（Prefix Caching）：复用相同系统提示词的预计算结果；
  • 连续批处理（Continuous Batching）：按需动态加入/完成请求，减少空等。

第 6 章 · 微调（Fine-tuning）与 PEFT

6.1 为什么要微调

当提示词工程 / RAG 不足以满足特定需求时，需要微调——用领域数据继续训练模型，让它学会特定风格、格式、任务或知识。典型场景：

  • 输出严格遵循特定 JSON 格式 / 企业风格；
  • 掌握某个垂直领域的专有术语与业务逻辑；
  • 在私有数据上持续学习，且不想每次都带长提示词。
⚠️ 微调不是万能的：它主要改变"行为/风格/少量知识"，无法真正"记住海量新事实"（那个是 RAG 的活，见第 8 章）。先想清楚到底该用微调还是 RAG。

6.2 全参数微调 vs 参数高效微调（PEFT）

全参数微调（Full FT）：更新所有权重，效果好但显存与算力开销巨大。对 7B 模型单卡几乎跑不动。

PEFT（Parameter-Efficient Fine-Tuning）：只训练一小部分新增参数，冻结原模型，成本极低、效果接近。主流方法：

方法思路特点
LoRA冻结原权重，注入低秩可训练矩阵最主流，显存省、效果好
QLoRALoRA + 4-bit 量化基座消费级显卡也能微调大模型
Prefix / Prompt Tuning学一组可训练前缀向量改动极小
Adapter插入小型可训练模块类似 LoRA 思路

6.3 LoRA 原理

LoRA（Low-Rank Adaptation）假设：微调对权重矩阵的改变是"低秩"的。于是把增量写成两个小矩阵的乘积：

W' = W₀ + ΔW = W₀ + B·A
  W₀: 冻结的原始权重
  A:  小的可训练矩阵 (r × d)
  B:  小的可训练矩阵 (d × r)
  r:  秩（通常 8/16/32），越小越省参数
  训练时只更新 A、B，原始 W₀ 不动

好处：训完只需保存很小的 adapter（几 MB~几百 MB），可叠加多个 LoRA 适配不同任务，随时切换。

6.4 实操：用 Hugging Face + PEFT 微调

典型最小流程（以 LoRA / QLoRA 为例）：

# 1) 加载基座模型（QLoRA 用 4bit 量化）
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct",
    torch_dtype=torch.bfloat16,
    load_in_4bit=True          # QLoRA 关键
)
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")

# 2) 配置 LoRA
lora = LoraConfig(
    r=8, lora_alpha=16, lora_dropout=0.05,
    target_modules=["q_proj","k_proj","v_proj","o_proj"],
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora)

# 3) 用 SFTTrainer 训练（数据为指令-回答对）
from trl import SFTTrainer, DataCollatorForCompletionOnlyLM
trainer = SFTTrainer(
    model=model, train_dataset=dataset,
    args=TrainingArguments(output_dir="./lora_out", per_device_train_batch_size=1),
)
trainer.train()

# 4) 保存并合并
model.save_pretrained("./lora_adapter")
merged = model.merge_and_unload()
merged.save_pretrained("./model_merged")

6.5 微调数据准备要点

  • 数量：几百~几千条高质量样本即可见效，不求海量；
  • 质量 > 数量：宁缺毋滥，避免矛盾样本；
  • 覆盖性：覆盖各种指令形态、边界情况、拒绝回答场景；
  • 一致性：格式统一（JSON、语气、长度）；
  • 去重去污染：避免重复样本过拟合、避免测试数据泄露。

第 7 章 · 提示词工程与结构化输出

7.1 什么是提示词工程

提示词工程（Prompt Engineering）= 通过设计输入来引导模型稳定、高质量地输出。它零成本、见效快，是入门大模型应用的第一步技能。

核心认知：模型是"概率机"，提示词越清晰、约束越多、示例越明确，输出就越可预期。你不是在"命令"，而是在给一台概率机提供充分的上下文约束。

7.2 提示词的基本组成

一个高质量提示词通常包含：

  1. 角色（Role）：你是谁/扮演什么（"你是一名资深法务"）；
  2. 任务（Task）：要做什么，动词明确（"总结、翻译、生成、分类"）；
  3. 上下文（Context）：背景信息、材料、约束；
  4. 格式（Format）：输出的结构（JSON、表格、要点、字数）；
  5. 示例（Example）：给 1~3 个输入输出样例；
  6. 边界（Constraints）：不要做什么、不确定时怎么办。
【角色】你是一名资深中文编辑，擅长润色与提炼。
【任务】把下面这段文字改写成更专业、简洁的版本。
【要求】
- 保留原意，去掉口语化表达
- 控制在 80 字以内
- 输出仅一行，不要加解释
【原文】...（这里放原文）

7.3 常见提示词技术

技术说明适用
Zero-shot直接下指令，不给示例简单任务
Few-shot给 2~8 个输入输出示例需要稳定格式/行为
角色扮演设定专业角色提升专业性/语气
思维链 CoT让模型"一步步思考"再作答复杂推理/数学

自我反思生成后再让其检查修正提升质量

7.4 思维链（Chain-of-Thought, CoT）

对数学、逻辑等复杂问题，直接问容易出错。让模型先把推理过程写出来，再给结论，正确率显著提升：

❌ 直接问：一个篮子里有3个苹果，又放进来5个，拿走2个，还剩几个？
✅ 引导思考：
"请一步步推理，最后给出结论：
第一步：开始有 3 个苹果
第二步：放入 5 个，共 8 个
第三步：拿走 2 个，剩 6 个
所以，还剩 6 个。"
结论：6 个

进阶：ReAct（Reason+Act）让模型"思考-行动-观察"循环，是 Agent 的核心（见第 9 章）；Tree-of-Thoughts（ToT） 让模型探索多条推理路径择优。

7.5 结构化输出（JSON / 表格）

工程上常需要模型返回结构化数据。两种思路：

  • 软约束：在提示词里明确格式 + 给 JSON 示例，模型通常能遵守；
  • 硬约束（推荐）：用约束解码 / 函数调用（Function Calling），从机制上强制输出合法 JSON，见第 9 章工具调用。
请只返回如下 JSON，不要输出其他内容：
{"title": "...", "summary": "...", "tags": ["..."]}
⚠️ 依赖软约束时，务必做解析兜底（正则/JSON 修复），别假设模型 100% 返回干净 JSON。

7.6 系统提示词（System Prompt）

把"角色、规则、边界、格式、安全"等稳定不变的约束放进系统提示词，用户输入放用户消息，让模型在固定基调上响应。这是搭建 Agent / 产品的关键。

【系统提示词】你是一个订单客服助手。
- 只基于知识库内容回答，不编造。
- 语气专业、简洁。
- 若无法回答，明确说"请咨询人工客服"。
- 所有输出为中文。

7.7 提示词注入与防护

提示词注入指恶意文本试图覆盖系统指令（如网页里的隐藏文本诱导模型泄露数据）。防护：

  • 把用户输入与系统指令隔离（分隔符 / 角色分离）；
  • 对输入做过滤/检测（拦截"忽略以上指令"等模式）；
  • 重要操作二次确认、限制工具权限；
  • 不把不可信文本直接拼进系统提示词。

7.8 提示词工具与库

  • 提示词模板库：预置常用角色/场景模板（如工作目录里的 Prompt-Template-Library）；
  • LangChain / Instructor：结构化输出与链式调用工具；
  • OpenAI 结构化输出 / Pydantic：强制 schema 校验。

第 8 章 · RAG 检索增强生成

8.1 为什么需要 RAG

LLM 的训练数据有截止时间，无法知道你的私有/最新资料，还容易幻觉（编造）。RAG（Retrieval-Augmented Generation）的解决思路是：先生成时先检索相关资料，把资料塞进提示词，再让模型基于资料作答。相当于"给模型临时配一个知识库"。

✅ RAG 相比微调的优势：知识可即时更新、不改变模型、可追溯到来源、成本低。是绝大多数"私有知识问答"场景的首选。

8.2 RAG 核心流程

   [离线] 建立知识库
   文档 ──分块(Chunk)──▶ 向量化(Embedding) ──▶ 存入向量数据库
                                                    ▲
   [在线] 用户提问                                        │
   问题 ──▶ Embedding(问题) ──▶ 向量相似度检索 ──▶ 命中 Top-K 文档
        │
        ▼
   组装提示词(问题 + 检索到的文档片段)
        │
        ▼
   大模型生成答案(可附带来源)
💡 一句话记住 RAG：先检索（Retrieval），再生成（Generation），所以叫"检索增强生成"。本质就两件事——先从资料库里捞出相关内容，再让模型基于这些内容回答。企业里的知识助手、智能客服，大多就是这么做的。
🤔 为什么不能直接把整本文档丢给模型？假设产品手册有上百上千页：① 模型有上下文窗口上限，读不下就会"读了后面忘前面"，准确率没保障；② 每次都要带上厚厚一本，推理成本暴涨；③ 输入越多，模型消化越慢，回答速度受拖累。所以正确思路是：只挑出真正相关的几个片段，连同问题一起给模型——这正是 RAG 的活。

8.2b 通俗拆解：RAG 全流程的五个环节

RAG 整体分两大块：提问前的"数据准备"（分片 + 索引）和提问后的"回答问题"（召回 + 重排 + 生成）。

环节阶段通俗理解一句话原理
① 分片（Chunking）提问前把厚厚的手册"拆成小块"按字数 / 段落 / 章节 / 页码把文档切成多份片段
② 索引（Indexing）提问前给每个小块"贴检索标签"用 Embedding 把每段文本变向量，连同原文一起存进向量数据库
③ 召回（Retrieval）提问后快速海选出"大概相关"的小块把问题向量化，与库中片段算相似度，粗筛出 Top-10
④ 重排（Rerank）提问后对海选结果"精挑细选"用 Cross-Encoder 模型精算，从 10 份里再挑出最相关 3 份
⑤ 生成（Generation）提问后模型照着材料作答把问题 + 3 个片段一起发给大模型，产出最终答案
🎯 为什么召回还要"重排"多此一举？像公司招人分两轮：召回 = 简历粗筛（候选多，只能用低成本方法快速过滤，准确率低没关系）；重排 = 面试精挑（人少了，用贵的模型仔细判断）。召回用向量相似度（便宜、快、准头差），重排用 Cross-Encoder（贵、慢、但准）。粗筛 + 精挑，效果远好于一步到位。

8.4 文档切块（Chunking）技巧

  • 块大小：通常 300~1000 token 一块，过大噪声多、过小信息不全；
  • 重叠（Overlap）：相邻块留部分重叠，避免切断句子语义；
  • 按结构切：优先按标题/段落/语义边界切，而非纯字符；
  • 保留元数据：记录每块的来源、标题、页码，方便溯源。

8.5 向量检索与混合检索

📚 先补三个基础概念（视频版通俗解释）：
  • 向量（Vector）：数学里"有大小、有方向"的量，用一串数字（数组）表示，数组长度就是"维度"。RAG 里用的向量维度常常几百甚至几千，维度越大承载的信息越丰富。
  • Embedding（嵌入）：把文本变成向量的过程。核心魔法在于——语义相近的文本，转换后的向量也相近（"马克喜欢吃水果"和"马克爱吃水果"的向量很近，"天气真好"则离得很远）。这样就能靠"向量距离"判断两句话是否相关。这一步由专门的 Embedding 模型完成，选型可参考 MTEB 排行榜。
  • 向量数据库：专门存储和查询向量的数据库，为向量检索做了优化，内置相似度计算函数。注意它不只存向量，还存原始文本——向量只是中间结果，最终喂给模型的还是原文。
  • 向量相似度：衡量"两个向量多像"的数值。常见三种算法：余弦相似度（算夹角，夹角越小越像）、欧式距离（算直线距离，距离越小越像）、点积（考虑方向 + 长度，同向越长值越大）。
  • 向量检索：语义相似，适合"意思相近但字面不同"；
  • 关键词检索（BM25）：精确匹配，适合专有名词/编号；
  • 混合检索（Hybrid）：两者结合（RAG Fusion / 加权），召回更全，工程上推荐。

8.7 RAG 评估指标

  • 检索质量：Recall@K、Precision@K、NDCG（命中相关文档的比例）；
  • 生成质量：忠实度（Faithfulness，答案是否基于检索内容）、答案相关性、覆盖度；
  • 端到端：人工评审 / LLM-as-judge 打分。

第 9 章 · AI Agent 与工具调用

9.1 什么是 AI Agent

Agent（智能体）是能自主规划、调用工具、与环境交互、达成目标的 AI 系统。相比"一次问答"，Agent 是一个能多步思考 + 多步行动 + 根据结果调整的闭环。

💡 关键转变：从"一次生成"到"工作流（Workflow）"。大多数人用 LLM 是"一次性提示它从头写到尾"（就像让人一口气不回头地写完一篇论文，效果往往一般）。而生成式工作流更像人写论文的过程：先列大纲 → 查资料 → 写初稿 → 反思哪里要改 → 再修改……反复迭代。过程可能更慢，但产出质量显著提升。Agent 的本质就是把复杂任务拆解成小步骤，逐个交给 AI 执行并不断检查。
🎯 最重要的技能：任务拆解。把一个大目标（写研究报告、回客户邮件）拆成离散的小步骤，再为每步搭组件——这套"拆解能力"直接决定你能构建多强的工作流。

9.1b 自主性程度（不是"是或不是"，而是"多自主"）

别纠结"这算不算真正的 Agent"——更实用的看待方式是把它当形容词：系统可以有不同程度的自主性。

自主性特点例子
低自主步骤序列由开发者预先硬编码，LLM 只生成文本内容固定的"生成关键词→调用搜索→抓网页→写论文"流水线
半自主模型可选择用哪些工具，但工具集预定义模型决定"要不要搜一下、搜哪个"
高自主模型自主决定步骤序列，甚至能写新函数/新工具规划 Agent、能创建可执行工具的系统
✅ 实用建议：低自主的流程应用最广、最可控，为众多企业创造了大量价值；高自主虽强大但更不可预测、难控制，属于研究前沿。起步先从低自主做起。
📈 工作流真的能提升效果吗？吴恩达团队在 HumanEval（代码基准）上验证：GPT-3.5 直接写代码正确率仅 40%，GPT-4 提升到 67%；而用工作流技术（让模型写完再反思、自我检查）包装后，即使是旧模型也能显著提升，甚至接近更贵模型的水平。结论：自主工作流对最强模型同样有效，不是只有小模型才需要。

9.2 核心机制：ReAct（推理 + 行动）

ReAct 让模型交替输出"思考（Thought）→ 行动（Action）→ 观察（Observation）"，像人一样边想边做：

Thought: 用户想查北京的天气，我需要调用天气工具。
Action: get_weather("北京")
Observation: 晴，25℃
Thought: 已获得天气，直接回答用户。
Action: 完成。今天的北京是晴天，气温 25℃。

9.2b 四大设计模式（吴恩达总结）

把复杂工作流"序列化"后，你会发现四大关键设计模式反复出现。它们是搭建 Agent 的基础构件。

模式核心思想例子
反射（Reflection）让模型审查自己的输出并迭代改进写代码→让模型检查→反馈"有 bug"→让模型改出 v3
工具使用（Tool Use）给模型可调用的工具，让它动手执行给联网搜索工具问"最好的咖啡机"，或给代码执行工具算复利
规划（Planning）让模型自己决定行动顺序（而非预先硬编码）HuggingGPT：让模型拆解"生成图像→描述→配音"并依次调用
多智能体（Multi-Agent）多个角色化 Agent 分工协作像虚拟软件公司：CEO/程序员/测试员/设计师协作；或调研+文案+编辑三人组
🎬 反射 = 让 AI 当自己的"审稿人"：把它的输出回喂给它，让它挑毛病再改。可引入外部反馈（如真正运行代码看是否报错）。
🧩 多智能体像组团队：研究员找资料、营销写文案、编辑润色。更难控制（无法预知每个 Agent 行为），但研究显示对复杂任务（写传记、下棋）常有更好结果。

9.3 工具调用（Function Calling）

让模型结构化地声明"我要调用哪个工具、传什么参数"，再由你的代码真正执行并返回结果。这是 Agent 与外部世界（API、数据库、代码）连接的关键。

// 定义工具
{
  "name": "get_weather",
  "description": "查询指定城市的天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名"}
    },
    "required": ["city"]
  }
}

// 模型可能返回
{"name":"get_weather", "arguments": {"city":"北京"}}

9.3b MCP：模型上下文协议 —— 工具调用的"USB-C 标准"

9.3 节的 Function Calling 有个痛点：每家 LLM 厂商的格式不同——OpenAI 有自己的 Function Calling 格式，Claude 有 Tool Use 格式，国产模型也各有各的 schema。你想让同一个工具同时服务不同 LLM，就得为每家单独适配，碎片化严重。

2024 年 11 月，Anthropic 开源了 MCP（Model Context Protocol，模型上下文协议），试图像 USB-C 统一充电口一样，统一 AI Agent 与工具之间的通信标准。到 2025 年 Agent 应用爆发后，MCP 迅速从"好主意"变成"事实标准"，已获 Claude、GPT、Llama、DeepSeek、通义等主流大模型支持。

✅ 一句话理解：Function Calling 是 LLM 层面的"调用接口"（厂商私有），MCP 是基础设施层面的"通信标准"（开放协议）。MCP 底层甚至可以用 Function Calling 做调用机制，但向上提供了更丰富的能力。

（1）设计灵感：从 LSP 到 MCP

MCP 的设计灵感来自软件开发领域的 LSP（语言服务器协议）——LSP 让"语言能力"从"编辑器"中解耦，一个语言服务器可对接 VS Code、Vim 等所有编辑器。MCP 同理：让"工具能力"从"AI 应用"中解耦，一个工具服务器实现对接所有 LLM。

对比LSPMCP
背景不同 IDE 对同一语言的补全/诊断各不同不同 LLM 对同一工具的调用方式各不同
核心思路将"语言能力"从"编辑器"解耦将"工具能力"从"AI 应用"解耦
价值统一了语言工具生态统一了 AI Agent 工具生态

（2）Host-Client-Server 三方架构

┌──────────────┐      ┌──────────────┐      ┌──────────────┐
│    Host      │◄────►│    Client    │◄────►│    Server    │
│   (宿主应用) │      │  (协议客户端) │      │  (工具服务)  │
└──────────────┘      └──────────────┘      └──────────────┘
典型: Claude Desktop    典型: MCP SDK        典型: 天气/数据库/文件
      VS Code+Copilot       (Python/Java/TS)       GitHub MCP
角色职责类比
Host（宿主）承载 LLM 的用户应用（Claude Desktop、IDE 插件、自定义 AI 应用），协调 LLM 与工具的交互浏览器
Client（客户端）MCP 协议通信端，由 Host 管理，与 Server 建立 1:1 连接、维护会话状态。一个 Host 可管理多个 Client浏览器中的 Tab
Server（服务器）提供具体工具能力的服务端（天气、数据库、文件系统等），通过 MCP 协议暴露能力。一个 Server 可被多个 Client 连接Web 服务器
⚠️ 关键设计：Host 与 Server 之间不直接通信，所有通信通过 Client 中转。底层消息格式为 JSON-RPC 2.0。

（3）三大核心能力（原语）

原语作用典型场景
Tools（工具）可调用的函数/方法，对应 Function Calling 场景天气查询、数据库 CRUD、API 调用、文件操作
Resources（资源）可通过 URI 寻址的数据资源，用于数据读取而非操作执行配置管理、知识库文档、系统状态、业务规则
Prompts（提示词模板）Server 端维护的可参数化提示词模板，Client 按需获取角色系统提示词库、工作流模板、多语言 Prompt 管理
💡 Resource vs Tool 的区别：Tool 是"做一件事"（执行操作），Resource 是"读一份数据"（提供上下文）。MCP 的 Resource 能力让工具可以动态暴露数据，应用按需加载，而非把所有数据一次性塞进 Prompt——解决了上下文管理痛点。

（4）传输协议：STDIO vs HTTP SSE

维度STDIO（标准输入输出）HTTP SSE（Server-Sent Events）
通信方式进程间通信（stdin/stdout）HTTP 长连接（SSE 推送）
适用场景本地开发、桌面应用、IDE 插件分布式部署、微服务、云端
性能低延迟（无网络开销）有网络延迟（但支持远程）
扩展性受限于单机可水平扩展、负载均衡
安全依赖操作系统进程隔离需 TLS / OAuth2 网络层安全
✅ 选型建议：本地开发/调试 → STDIO（简单直接，零网络配置）；生产环境/远程部署 → HTTP SSE（支持网络传输和水平扩展）。

（5）完整工作流程（8 步）

步骤1: 初始化       Host启动 → 创建Client → Client向Server发送 "initialize" 请求
步骤2: 能力协商      Server返回支持的协议版本和能力 → 双方协商确定功能集
步骤3: 会话建立      Client发送 "initialized" 通知，正式建立会话
步骤4: 能力发现      Client发送 "tools/list" → Server返回可用工具列表（名称、描述、参数Schema）
步骤5: 用户请求      用户在Host中发起自然语言请求（如"查上海天气"）
步骤6: LLM推理       Host将请求 + 工具列表发给LLM → LLM决定调用哪个工具、传什么参数
步骤7: 工具调用      Host通过Client发送 "tools/call" → Server执行并返回结果
步骤8: 响应生成      LLM基于工具结果生成最终自然语言响应 → 展示给用户
🔑 核心价值在"步骤4：能力发现"：工具列表和 Schema 是动态获取的，而非硬编码。Server 端新增/修改工具，Client 端自动感知，无需重新部署。

（7）选型决策树

你的应用是否需要连接多个外部工具/数据源?
├── 否 → 只需单次调用简单API
│   └── 使用 Function Calling（足够简单，无需额外复杂度）
│
└── 是 → 需要集成多个工具
    │
    ├── 工具是否需要被多个不同 LLM 应用复用?
    │   ├── 否 → 单一 LLM、工具列表固定
    │   │   └── 使用 Function Calling
    │   └── 是 → 需跨应用、跨 LLM 复用
    │       └── 使用 MCP（核心优势：一次实现，到处使用）
    │
    ├── 是否需要动态发现工具能力?
    │   └── 是 → 使用 MCP（动态能力发现）
    │
    └── 是否需要向 LLM 提供动态上下文数据?
        └── 是 → 使用 MCP Resources
📌 核心决策原则：① 只服务单一 LLM、工具少且固定 → Function Calling；② 需要工具复用/动态发现/多 LLM → MCP；③ 本地部署优先 STDIO，远程部署优先 HTTP SSE。

（8）企业级部署要点

  • 安全边界：生产环境必须 HTTPS + TLS 1.2+，按 Tool/Resource 粒度做权限隔离，OAuth 2.0 授权；
  • 幂等性：tools/call 不保证幂等（重复调用有副作用），涉及写操作的工具需引入幂等键；
  • 流量控制：用限流/熔断保护 MCP Server（如 Resilience4j），防止过载；
  • MCP Gateway：大量 Server 时引入统一网关，集中处理认证、限流、审计、路由、协议转换、工具注册中心；
  • 审计日志：记录所有工具调用（调用者、参数、时间、结果），支撑可观测性。

（9）协议演进与生态

MCP 最新版本（mcp-2025-11-25）引入了多项重要增强：

  • Elicitation（启发式交互）：Server 可在工具执行中向用户请求额外信息，实现更智能的人机协作；
  • Progress Notification：长时间运行的操作可上报进度；
  • Resource 订阅：支持资源变更通知，客户端实时感知数据变化；
  • Tool/Resource/Prompt 列表变更通知：Server 端能力变更自动告知 Client；
  • Sampling 增强：Server 可请求 Client 代为调用 LLM 推理，实现双向协作；
  • OAuth 2.0 安全授权：为企业级部署提供标准化安全框架。
🌐 官方规范站点：modelcontextprotocol.io。框架层面，Spring AI 1.0+、LangChain 等主流框架已集成 MCP 支持。MCP 正从"工具调用标准化"向"多 Agent 编排、工作流标准化"方向演进，类似 npm 的 MCP Server 注册中心和工具市场也在快速涌现。
💡 和你的关系：你现在用的 TeleAgent 就支持 MCP——你可以在工具设置中注册 MCP 服务器（STDIO 或 StreamableHTTP），让 AI 助手拥有操作外部工具的能力。这就是 MCP"一次实现，到处使用"理念的实际落地。

9.4 记忆（Memory）

Agent 需要三种记忆：

  • 短期记忆：当前对话上下文（多轮历史）；
  • 工作记忆：规划中的步骤与中间结果；
  • 长期记忆：持久化的知识/偏好（常配合向量库或数据库）。

9.5 规划（Planning）

复杂任务需要拆解为可执行步骤：

  • 任务分解（Task Decomposition）：把大目标拆成子任务；
  • ToT / CoT：多路径推理与逐步思考；
  • 反思（Reflection）：做完后自我检查、修正；
  • 子 Agent（Sub-agents）：把子任务委派给专门的 Agent。

9.6 多 Agent 协作

多个 Agent 各司其职，分工协作处理复杂流程（如：规划 Agent + 检索 Agent + 编码 Agent + 审查 Agent）。代表框架：

  • AutoGen（微软）：多 Agent 对话协作；
  • CrewAI：角色化团队协作，易用；
  • LangGraph：图结构编排多 Agent 状态机。

9.7 Agent 的工程挑战

  • 错误传播：某一步出错会放大；需加异常处理、重试、预算上限；
  • Token 消耗大：多步循环消耗大量上下文，需控制工具结果大小；
  • 安全风险：工具权限越界、提示词注入、任意代码执行——必须最小权限 + 白名单 + 人工确认关键操作；
  • 可观测性：记录每步思考/工具调用，便于调试。

框架定位

第 10 章 · 评估与可观测性

10.1 为什么评估很重要

LLM 输出非确定、易幻觉，无法像传统软件那样"跑对了就行"。做 AI 应用必须持续评估质量，否则上线后难以发现问题、迭代没有依据。评估是工程化的地基。

10.2 模型能力评估（Benchmark）

维度评测集衡量什么
综合知识MMLU、C-Eval、CMMLU跨学科知识广博度
推理GSM8K（数学）、BBH数学/逻辑推理能力
代码HumanEval、MBPP代码生成正确性
中文理解C-Eval、SuperCLUE中文语境能力
指令遵循IFEval是否严格遵守指令/格式

10.3 应用评估：三类指标

  • 质量指标：准确性、忠实度、相关性、完整性、格式合规；
  • 性能指标：首 token 延迟、总延迟、吞吐（tokens/s）、错误率；
  • 成本指标：每次请求 token 消耗、推理成本、缓存命中率。

10.4 人工评估 vs LLM-as-judge

  • 人工评估：最可靠，但贵、慢、难规模化——用于抽检与小样本；
  • LLM-as-judge：用强模型给输出打分，可规模化；需注意位置偏差、自我偏好，最好用开源强模型打分并做一致性校验。
// LLM-as-judge 打分提示词示例
你是一个评估员。请基于"忠实度、相关性、格式"给回答打分(1-5)：
标准答案：...
模型输出：...
请给出分数和简短理由。

10.5 幻觉（Hallucination）检测

幻觉 = 模型输出与事实/给定资料不符。缓解与检测：

  • 用 RAG 约束到资料范围、要求"只依据资料回答"；
  • 要求模型给出引用来源，便于人工核验；
  • 用 FactScore / 忠实度打分 评估输出与资料的一致性；
  • 关键场景加规则校验（数值、枚举、格式）。

10.6 可观测性（LLMOps）

生产环境的 AI 应用需要监控：

  • 追踪（Tracing）：记录每一次请求的提示词、工具调用、输出、token 数；
  • 指标（Metrics）：延迟、吞吐、错误率、成本；
  • 日志与回放：保存样本，出问题时复现；
  • 评估回填：定期对线上样本评分，发现质量退化。

10.8 建立你自己的评测集

针对你的应用，准备50~200 条真实/代表性用例（含边界与拒绝场景），每次改动后跑一遍对比，防止"修好一个、坏掉一片"。这是低成本、高价值的工程习惯。

💡 别只凭"感觉好不好"上线。建立最小评测集，让每个改动都有量化依据——这是专业工程师和爱好者最重要的区别。

第 12 章 · 学习路线与资源清单

12.1 学习误区

  • 盲目堆资料：收藏一堆课程却不动手，越学越乱；
  • 只看不练：不写代码、不跑项目，看完就忘；
  • 跳过基础直接上项目：Transformer 没搞清就搭 Agent，出问题无从下手；
  • 没目标：不知道想成为"提示词工程师 / 部署工程师 / 应用开发 / 训练算法"，方向不清。
✅ 核心心法：明确目标 → 小步实践 → 项目驱动。理论为辅，动手为主。

12.2 分阶段学习路线

阶段一：入门（2~4 周）——会用 AI

  • 理解 LLM 是什么、怎么用（本文第 1、7 章）；
  • 每天用 ChatGPT/通义/Kimi 等做实际任务，练提示词；
  • 会用 API 写一个最简单的对话脚本（Python + OpenAI 兼容接口）。

阶段二：应用开发（4~8 周）——会用 AI 做产品

  • 掌握提示词工程 + 结构化输出（第 7 章）；
  • 搭建一个 RAG 问答（第 8 章），把资料喂给模型；
  • 学 LangChain/LlamaIndex/Dify 搭一个可用的 Agent（第 9 章）；
  • 建立最小评测集，评估效果（第 10 章）。

阶段三：部署/微调（可选的进阶，4~8 周）——会自己训/自己部署

  • 学 Python + PyTorch 基础、模型加载与推理（第 5、6 章）；
  • 用 Ollama 本地跑开源模型；
  • 用 LLaMA-Factory 做一次 LoRA 微调（第 6 章）。
